# 通用化可行性报告 —— 能否让 ShellVMP 不只保护 bash？

> **结论先行**：**"快速做一个通用补丁"做不到**，但原因和直觉相反 —— 瓶颈**不是语法**，是**密钥链把解释器语义烧进了密文**。
>
> 而你说的那个痛点（"只能用于 bash 防护太拉了"）里，**真正属于 bash 限制的部分只占约 20%**。剩下 80% 是"目标机可能没装 bash"——**这个问题项目已经解决了**，只是没写成默认路径、没宣传。
>
> 本文档把三层阻塞拆到行号、给出**功能剥离表**（哪些能砍、哪些不能、砍了损失什么），以及三档路线的真实工作量。

---

## 一、实测数据（不是推演）

沙箱实测环境：x86_64 / Ubuntu 22.04，bash 5.2.21、dash 0.5.12、zsh 5.9。

| shell | 跑 V6 生成端 | 跑 V6 产物 | 失败形态 |
|---|---|---|---|
| **bash** | ✅ | ✅ | — |
| **dash** | ❌ `Syntax error: "(" unexpected`（93 行） | ❌ `declare: not found` | 语法错，**报错可见**，好排查 |
| **zsh** | ❌ 静默退出（rc=0、零输出） | ❌ 密钥链错 | **静默死**，最难排查的形态 |

两个值得单独拎出来的实证：

**① zsh 跑生成端为什么会"静默成功"？**

`v6/shell_script_obfuscator_v6.sh:2993`：

```bash
if [[ "${BASH_SOURCE[0]}" == "${0}" ]]; then
    main "$@"
fi
```

zsh 下 `BASH_SOURCE[0]` 未定义 → 展开为空 → 条件恒假 → **不调 `main`，什么都不做，rc=0**。用户会以为"跑完了"，实际产物根本没生成。

**② 各 shell 的 `$RANDOM` 完全不是一回事**

```
bash:  RANDOM=1234 → 30658 14076 1273
zsh:   RANDOM=1234 → 8718 31363 7947      ← 算法不同
dash:  RANDOM=1234 → 1234 1234 1234       ← 根本没有 $RANDOM
```

dash 0.5.12 把它当**普通变量**处理：赋值后被原样读出三次。**这不是"算法不同"，是"变量不存在"**。

## 二、三层阻塞（逐层拆到行号）

### 第 1 层 · 生成端语法 —— **这一层不用改**

V6 生成器自身（2995 行，非空非注释 1970 行）用了大量 bash 专有语法：

| 语法 | 出现次数 | 性质 |
|---|---|---|
| `<<<` here-string | 24 | 生成器自身逻辑 |
| `[[ ]]` | 17 | 生成器自身逻辑 + **部分在产物模板里** |
| `$RANDOM` | 11 | 生成器自身逻辑 + **产物模板里有关键用法** |
| `local -a` | 10 | 生成器自身逻辑 |
| `EPOCHREALTIME` | 5 | **全在产物模板里** |
| `declare -a` | 4 | **全在产物模板里** |
| `${var//}` | 3 | **全在产物模板里** |
| `=~` | 2 | 生成器自身逻辑 |

**关键判断：生成器可以继续用 bash 跑。** 不需要把 1970 行改写成 POSIX。
需要改的只是**它产出的模板字符串**。这一层是"虚惊"。

### 第 2 层 · 产物运行期语法 —— 可改，但改动面大

产物骨架（模板生成，位于 `2200-2600` 行）里有：

| 位置 | 内容 | 改法 |
|---|---|---|
| 2239 / 2246 / 2275 / 2279 | `echo "declare -a ${N_C}"` 等 4 处数组声明 | dash 无数组 → 降级空格分隔 + `set --` |
| 2504 | `[[ "$err" != *"here-document"* ]]` | → `case "$err" in *here-document*) ;; esac` |
| 1116 / 1130 / 1131 | `<<<` here-string（`read -a _ial <<< "$_b"`、`source /dev/fd/9 9<<< "$_code"`） | → `printf ... \| read` 或临时文件（**性能明显下降**） |
| 1103 / 1109-1110 | `EPOCHREALTIME` + `${_nw//.}` | → `date +%s%N` 或去掉超时检测 |
| 1891 / 1895 | DETS 里 `[[ $- == *x* ]]` | → `case $- in *x*) ...` |

**真正的痛点是数组**：解释器里 `${_c[$_p]}`、`${#_c[@]}`、`"${_ial[@]}"` 这类下标访问遍布全篇。
"降级为空格分隔字符串"这句话听起来简单，实际要改掉**所有**下标访问点。这是"可改但不好改"的典型。

### 第 3 层 · 密钥链 —— **决定性，但比预想的窄**

编译期与运行期必须逐项对称的公式（`1876` 行 ↔ `2452` 行）：

```
__MK__ = H( SEED + FP + DV + IH + $-  + VERSINFO[0] + len(VERSINFO[]) )
                                  ↑         ↑              ↑
                              bash "hB"   bash 主版本    6（bash 数组长度）
```

**逐因子实测判定**（本报告最有价值的表）：

| 因子 | 实际值 | 可移植性 | 结论 |
|---|---|---|---|
| `SEED` | 16 位随机字符串 | ✅ **无关** | 与 shell 无关 |
| `FP` | `collect_platform_entropy` 输出 | ✅ **无关** | 采集 `uname`/`/proc`，同一台机器换 shell 值不变 |
| `DV` | `collect_device_entropy` 输出 | ✅ **无关** | 同上 |
| `IH` | `sha512(V6 自产解释器文本)[0:16]`（1863 行） | ✅ **无关** | **关键发现**：哈希的是 **V6 自己生成的解释器文本**，不是宿主 shell 二进制。纯可移植 |
| `$-` | 硬编码字面量 `"hB"` | ⚠️ **参数化即可** | bash 得 `hB`、dash 得空串、zsh 得 `569X` → 换成配置项 |
| `VERSINFO[0]` | `BASH_VERSINFO[0]` | ⚠️ **注入常量即可** | 改成"目标解释器版本标签"，无需真读 |
| `len(VERSINFO[])` | 字面量 `6` | ⚠️ **注入常量即可** | 同上 |

> **7 个因子里 4 个本来就无关，3 个是"注入一个常量"的机械操作。**
> 这一层的改动面**比预期小得多**。真正的硬骨头在下面。

## 三、真正的硬骨头：`$RANDOM` 状态机

运行时 `_am()`（`1089` / `1207` 行）是**产物里唯一推进密钥链的地方**：

```bash
_am() {
    _rs=$(( (_rs * 1103515245 + 12345) & 0x7fffffff ))
    RANDOM=$_rs          # ← 重播种
    _ra=$RANDOM          # ← 消费两次
    _rb=$RANDOM          # ← 这两个值掺进 _mk
    ...
    _mk=$(printf '%s%d%d%d' "$_mk" "$_p" "$_ra" "$_rb" | "$_S5")
    _mk=${_mk:0:16}
}
```

编译期 `sim_random_next()`（`799-820` 行）是**从零复刻**的 glibc `random()`：Park-Miller（`s*16807 - 2836*h`）+ `(s>>16)^(s&65535)` 折叠 + `do-while` 去重，与 bash 的 `$RANDOM` **逐比特对齐**。

我验证过它的精度 —— 喂 `1234` 进去：

```
编译期模拟器输出:  30658 14076 1273
bash 实测输出:     30658 14076 1273     ← 完全一致
```

**这正是问题所在**：

- **dash**：没有 `$RANDOM`（实测得字面量 `1234`）→ 要么逆向出一份 dash 版随机数发生器，要么**把整条密钥推进机制换掉**。换掉意味着同步重写编译期模拟器 + 逐块对拍。
- **zsh**：有 `$RANDOM`但**算法不同**（实测序列 8718/31363/7947 ≠ bash 的 30658/14076/1273），且 `$-` 受用户 `.zshrc` 的 `setopt` 影响 —— **同一个产物，A 用户跑得通、B 用户装了自定义 `.zshrc` 就跑不通**。

**这一层没有任何"只改模板"的余地。** 它不是语法问题，是"你必须为目标 shell 重新实现一个随机数发生器，并保证与运行期逐比特一致"。

### 顺带一提：`$_` / `$?` 绑链

编译期 `simulate_execution()`（`333-424` 行）会用 bash **真跑一遍**用户脚本，捕获每个块执行后的 `$_`（上条命令最后一个参数）和 `$?`，把这些值掺进运行期密钥链。

- **dash 没有 `$_`** —— 编译期与运行期都是空串，链子"恰好自洽"，但这层保护直接归零（攻击者也不用模拟了，因为它是常量）。
- **bash 与 dash 的 `$?` 在多数场景相同**，但管道退出码、算术失败等边界有分叉，需要真机逐条对拍。

## 四、功能剥离表（你要的那份）

你的思路是对的：**能剥离的剥离，不能剥离的标出来排期**。下表是逐功能判定：

| 功能 | 是否与 shell 语义耦合 | 通用版可否保留 | 剥离后安全损失 |
|---|---|---|---|
| encrypt-then-MAC 完整性校验 | ❌ 否 | ✅ **保留** | 无 |
| 一层壳 / 密钥分离 / passkey | ❌ 否 | ✅ **保留** | 无 |
| 垃圾块 / 诱饵块 | ❌ 否 | ✅ **保留** | 无 |
| per-build 常量随机化 | ❌ 否 | ✅ **保留** | 无 |
| V7 ELF 线 + `v7_wrap.sh` | ❌ 否（**已是纯 POSIX sh**） | ✅ **保留** | 无 |
| 环境指纹 / 反调试 DETS | 🔸 部分（`[[ $- == *x* ]]`） | ⚠️ **改写成 POSIX `case`** | 无 |
| `$-` / `VERSINFO` 指纹掺入密钥 | ✅ 是 | ⚠️ **参数化**（注入目标 shell 常量） | 基本无 |
| `declare -a` 数组容器 | ✅ 是（dash 无数组） | ⚠️ **降级**为空格分隔 + `set --` | 无（纯工程改造） |
| **批量自修改（`_am` 密钥推进）** | ✅ **强耦合 `$RANDOM`** | ❌ **必须剥离** | **每批重加密的保护消失** |
| **`$_` / `$?` 执行结果绑链** | ✅ **强耦合** | ❌ **必须剥离** | **沙箱置换（curl→true 桩）防御消失** |
| V7-ISA 令牌化层 | ✅ 是（绑定 bash 5.2 源码结构） | ❌ **不移植** | 通用版无此层 |

**这解释了为什么"通用版"会快很多**：真正卡死的只有 3 项（`_am` 推进、`$_`/`$?` 绑链、ISA 令牌化），而它们恰好是**安全强度最高的那几项**。剥离后仍保留 encrypt-then-MAC + 密钥分离 + 一层壳 + 常量随机化 —— **依然是个像样的保护器**，只是不再是"必须真正模拟执行才能解开"那个级别。

## 五、一个必须说破的事实

> **"跨 shell"与"必须模拟执行"是同一枚硬币的两面。**

项目的整个安全模型（`ARCHITECTURE.md`）建立在：**攻击者必须真正模拟运行环境才能推导出密钥**。
而"让任意解释器都能跑"意味着**把环境语义从密钥里拿掉** —— 拿掉了，攻击者也不用模拟了。

所以这不是"实现得不够好"，是**设计目标本身的边界**。要跨 shell，就得接受"剥离第 3 层绑链"的代价。这应该是**一个有意识的取舍**，不是"补个丁"。

## 六、你的痛点，真实构成是什么

"只能用于 bash 防护还是太拉了" —— 拆开看：

| 痛点来源 | 是真限制吗 | 缓解方式 | 状态 |
|---|---|---|---|
| "目标机可能没装 bash"（adb shell 裸环境） | ❌ **不是限制** | `V7_SELF=1` 内嵌静态 bash，产物自带解释器 | ✅ **已实现**，只是没做成默认路径 |
| "要跨 CPU 架构分发（aarch64/armv7/x86_64）" | ❌ **不是限制** | `v7/static/` 已有 bionic + musl 双套 aarch64、x86_64 产物 | ✅ **已实现** |
| "外层包装要能在任意 shell 里解压" | ❌ **不是限制** | `v7_wrap.sh` 第 67 行就是 `#!/bin/sh`，注释明确"sh/bash/mksh/dash/busybox ash 均可执行" | ✅ **已实现** |
| "我手上的脚本是 dash/ash 写的" | 🔸 **部分是真限制** | bash 5.2 是 POSIX 超集，能解释**绝大多数** POSIX sh 脚本。真正不兼容的只有用了 dash/ash/zsh **专有语法**的少数 | 🔸 影响面小，但确实存在 |
| "产物想跑在 zsh 用户的机器上" | ✅ **真限制** | 受 `.zshrc` 影响，见上文 | ⚠️ 无解（除非剥离绑链） |
| "要保护的是 Python/Perl 脚本" | ✅ **真限制** | 超出 shell 保护范畴，是另一条产品线 | ⚠️ 不同的 VMP 方案 |

**结论：80% 的痛点已经解决了，只是没写清楚、没做成默认。** 剩下 20% 里，只有"dash/ash 专有语法脚本"是低成本可缓解的，"zsh 产物"和"跨语言"是真限制。

## 七、三档路线与真实工作量

### 档位 1 · 产品化（**半天**，推荐先做）

不碰任何跨 shell 移植，只做"把已有能力转正 + 说清边界"：

1. **`V7_SELF=1` 转正为默认推荐路径** —— 内嵌静态 bash，产物自带解释器，目标机无需装 bash。这是你 80% 痛点的正解，且**代码已经在跑**。
2. **输入面体检工具** `tools/sh_compat_check.sh` —— 二十行，`bash -n` + 行为对拍，快速判定"这个脚本 bash 吃不吃得下"。解决"我的脚本 bash 能跑吗"这个真问题。
3. **README 适用范围三句话** —— 把边界写成**设计约束**而不是缺陷：
   ```
   ✅ 支持：bash 5.1+（完整实现，生产验证）
   🟡 可移植：架构语言无关，方法论见 docs/PORTING.md
   ❌ 不支持：POSIX sh / dash / zsh 的产物运行（语言特性不足，非补丁可解）
   输入：任何 bash 能解释的脚本；产物：必须 bash 5.1+
   ```
4. **本文档 + 功能剥离表** 作为公开的路线图依据。

### 档位 2 · dash-only 子集 PoC（**3-5 天**）

只做 dash，**明确放弃 zsh**。必须完成：第 2 层数组降级 + 第 3 层三个常量参数化 + `_am` 密钥推进机制替换 + 编译期模拟器同步重写 + dash 真机逐块 `$?` 对拍。

> **止损点**：先做最小验证 —— 生成一个 dash 产物，看它**能否跑通第一个块**。跑不通就说明 `$RANDOM`/`$_` 死结比预估更硬，**立即停**，不要投入完整工程。

代价：产物失去 `$_` 维度的绑链强度（安全性略降），且**编译期机器上必须有 dash**。

### 档位 3 · 完整跨 shell（**2-4 周**，不推荐）

dash + ash + mksh + zsh。每个 shell 都要重新逆向 `$RANDOM` 算法并对拍，zsh 还要处理 `.zshrc` 依赖。**且每加一个新 shell 就要重做一遍。**

## 九、总结

1. **"快速做一个通用补丁"做不到** —— 卡点是密钥链里的 `$RANDOM` 状态机，不是语法。
2. **但你以为的痛点，80% 已经解决了** —— 内嵌 bash 让产物跨平台，`v7_wrap.sh` 已经是纯 POSIX sh。缺的是"写成默认路径 + 说清楚"。
3. **"通用化版本"可以很快**（半天），但它的内容不是"支持 dash"，而是**"把已有的跨平台能力产品化 + 把边界写诚实"**。
4. **真要做跨 shell，请先做档位 2 的止损验证**，并且明确知道代价是**剥离最高强度的三层绑链**。
5. **跨 shell 与"必须模拟执行"是同一枚硬币的两面** —— 这是设计边界，不是实现缺陷。
