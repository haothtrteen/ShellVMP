# 开源范围说明

> 这份文档明确说明：**哪些开源、哪些保留、为什么**。
>
> 写这份文档本身就是一种专业信号——避免"看起来缺了什么"的猜测，也让使用者清楚知道自己在用什么。

---

## 一、原则

> **开源"怎么想"，保留"怎么调"和"怎么用"。**

- **机制公开**不削弱安全性（Kerckhoffs 原则）：安全性应依赖**密钥**，不依赖**算法保密**
- 而且机制公开会让项目**更可信、更容易被引用**，也避免"别人抢先发论文说这是他做的"
- **参数与运维保留**才是实际优势所在

### 许可策略：双许可，而不是"开源 vs 闭源"的二选一

本仓库整体采用 **[AGPLv3](../LICENSE) + [商业授权](../LICENSE.COMMERCIAL)** 双重许可：

| | 开源路径（AGPLv3） | 商业路径 |
|---|---|---|
| 能不能用 | ✅ 免费 | 💰 需授权 |
| 能不能商用 | ✅ **可以**——只要你把修改版开源 | ✅ 可以，且**不必开源** |
| 能不能闭源 | ❌ 不行 | ✅ 这正是买授权的原因 |
| 网络服务（SaaS） | ⚠️ 必须向用户提供完整源码（第 13 条） | ✅ 无需开源 |

**为什么选 AGPLv3 而不是 MIT**：MIT 允许任何人拿走代码闭源商用、且不回报社区。
AGPLv3 把"用了就得开源"这条线钉死（含 SaaS 场景），**既保住了开源用户的自由，
又让"不想开源"成为唯一的付费理由**——这就是双许可的商业逻辑。同时 AGPLv3 是
OSI 认可的正式许可证，GitHub 可正确识别，不影响项目的开源身份与引用。

**用户的两条硬性要求，落脚点如下**：

1. **署名不可去掉**——任何分发形式（开源/闭源、改/不改、源码/二进制）都必须
   保留原始版权与许可证声明。这正是 AGPLv3 第 4、5 条；商业许可合同里也会重申。
2. **商用需授权**——"商用"在这里精确指"**闭源商用**"。开源商用是免费的、
   我们明确欢迎的（见 `LICENSE.COMMERCIAL` 第一节）。

## 二、分层清单

| 层 | 状态 | 理由 |
|---|---|---|
| **V6 混淆算法**（分块/绑链/跳跃密钥链/自修改） | ✅ **开源** | 教材级内容；算法公开不削弱安全性 |
| **V7 加载器 + 密码学核心** | ✅ **开源** | 同上。开源 = 更多人帮找 bug |
| **全套文档 / 方法论 / 心路历程** | ✅ **开源** | 最好的名片 |
| **工具**（lint / diag / 定位 / 对接） | ✅ **开源** | 工程工具本身就是价值 |
| **V7-ISA bash 补丁集**（anchors.py / isa_hook.c / 构建脚本） | ✅ **开源（= GPLv3 义务范围）** | 分发内嵌魔改 bash 的产物必须提供对应完整源码——这不是选择，是 bash 许可证的硬要求。且公开翻译**机制**不泄露保护强度（见下节） |
| **V7-ISA 表内容**（别名→真名映射，随产物加密） | ❌ **随产物走** | 表体加密 + MAC；不落仓库、不落磁盘明文 |
| **真机构建链路（特定环境适配）** | ❌ **保留** | 与具体业务环境绑定 |
| **最优参数组合预设** | ❌ **保留** | 公开"有哪些旋钮"，保留"最优旋钮组合" |
| **真机产物二进制** | ❌ **不分发** | 体积 + 隐私 |

> **注意**：这里的"开源"是**许可证层面**的——上表全部内容都以 AGPLv3 授权，
> 谁都可以取用（含商用），前提是遵守 AGPLv3。下表的"保留"指的是
> **不主动放进仓库**（不存在），而非"许可证不允许别人用"。

"保留"项若也要对外提供，走 **[商业授权](../LICENSE.COMMERCIAL)**：付费方在
合同约定范围内使用，无需承担 AGPLv3 的开源义务。这是双许可里"商业路径"的
实际交付物——**卖的不是代码，是省掉的开源义务 + 支持与责任承担**。

## 三、为什么 bash 补丁集开源不伤商业核心（许可证边界算账）

**GPLv3 索取的，恰好是项目哲学本来就公开的那部分。** 分发内嵌魔改 bash 的产物
时，"对应源码"= bash 全源码 + 编进二进制的我们的文件（isa_hook.c、crypto_isa.h、
v7_isa_key.h、v7_isa_syms.h）+ 构建脚本。逐项看泄露面：

| 文件 | 开源的实际代价 |
|---|---|
| `isa_hook.c` 翻译逻辑 | 零——Kerckhoffs 原则：机制公开，强度靠密钥 |
| `v7_isa_key.h`（表主密钥） | 零——它**本来就随二进制走**（rodata），dump 即得；开源与否不改变攻击者实际所得（诚实清单已承认 dump 边界） |
| `v7_isa_syms.h`（sym→真名） | 零——真名是公共命令名/保留字 |
| `anchors.py` 插桩点 | 降低复现门槛——但"锚点会漂移、校准要实测"的 know-how 本来就写在文档里 |

**不在任何 copyleft 范围内的商业核心**（自有代码，AGPL 只约束分发/服务，
不约束"闭源自用"）：V6 密钥链实现与最优参数、表生成器的商业版、
真机构建链路、SaaS 服务本身的运营。

> ⚠️ **与 MIT 时代的重要差别**：以前自有代码是 MIT，可以随便闭源分发；
> 现在是 AGPLv3，**自有代码的修改版一旦分发或对外提供网络服务，同样必须开源**。
> 想绕过 → 买商业授权。这是有意为之的设计，不是疏漏。

**两条线并存的意义（选型表）**：

| 你的场景 | 该走哪条线 | 为什么 |
|---|---|---|
| 自己用 / 开源项目 / 内部工具 | **bash 线**，AGPLv3 | 免费，且本来就打算开源，义务零成本 |
| 闭源分发产物给客户 | **bash 线 + 商业授权** | 用商业授权覆盖自有代码，bash 那层的 GPL 义务仍需履行 |
| 闭源分发且**连 bash 源码都不想给** | **mksh 线** | MirOS 宽松，只需保留声明 |
| 运营 SaaS，产物不下发 | **bash 线**，AGPLv3 | 用户脚本只在你控制的机器上跑，未触发分发；但**第 13 条**要求向服务使用者提供修改版源码，若这一点无法接受则需商业授权 |

### 豁免路线：换内嵌解释器，整条甩掉 GPL

GPL 义务跟着"**链接进哪个二进制**"走——不看代码在谁的仓库、谁写的。
若商业上需要**闭源分发产物**：把内嵌解释器换成宽松许可证的实现，
翻译运行时移植过去，即可闭源分发：

| 内嵌解释器 | 许可证 | 分发义务 | 代价 |
|---|---|---|---|
| **bash**（现状） | GPLv3+ | 开源补丁集（**零成本**，已开源） | 无 |
| **mksh** | MirOS（宽松） | **无**（保留版权声明即可） | V7 ISA 需移植（L1-L4 插桩 + 翻译实装）；**产物兼容性已 8/8 实证**，地基齐备 |
| zsh | MIT-like | 无 | 脚本收敛成本 + 解释器适配工作量最大 |

> 触发条件：只有"真的需要闭源分发产物"时才走 mksh 路线——那是 Plan B 的
> 最短路径，而不是默认路线。sh-hook（G1-G3 自动发现）正是那条线的现成地基。
> 另注：构建/发现期工具（sh-hook、v7_isa.py、anchors.py 本身）不链接进产物
> 二进制，**从来不在** GPL 义务范围内——它们开源与否与 GPL 无关。

> **注意区分两个"闭源"**：
> - **闭源分发产物** → 想甩掉的是 **bash 的 GPL 义务** → 换 mksh 内嵌解释器（技术方案）
> - **闭源分发/运营本项目本身的修改版** → 想甩掉的是 **自有代码的 AGPL 义务** → 买商业授权（法律方案）
>
> 两件事独立，可以同时需要。

## 四、如果你要用在商业项目

| 你想做 | 用开源的够吗 |
|---|---|
| 保护自己的 shell 脚本（自己也开源） | ✅ **够**——V6 + V7 完整可用，AGPLv3 免费 |
| 理解方法论并移植到别的语言 | ✅ 够（文档齐全，但移植版同样受 AGPLv3 约束） |
| 要 V7-ISA 的完整实现 | ⚠️ 需要自行校准插桩点（有文档指导） |
| 要经过实战调优的参数组合 | ❌ 需要自己调 |
| **闭源**集成进商业产品 | ❌ 不够，需要 **[商业授权](../LICENSE.COMMERCIAL)** |
| 运营对外 SaaS 且不想开源 | ❌ 不够，需要商业授权 |

## 五、贡献者注意（版权集中是双许可的前提）

双许可能成立，靠的是**版权集中**——版权人必须持有足以在两条路径下分发的完整权利。

> **向本仓库提交贡献（PR / 补丁）即表示你同意：将该贡献的版权
> （或足以支撑商业授权的完整权利）授予版权人。**

若你所在组织对这条有异议，请在提交前先联系我们（见 [`LICENSE.COMMERCIAL`](../LICENSE.COMMERCIAL)）。

其余欢迎的贡献类型：

- 🐛 **Bug 报告**：附**产物 + 复现命令 + 期望行为**
- 📖 **文档改进**：尤其是"你踩了什么坑"——这类内容最有价值
- 🧪 **测试用例**：请遵循"**逐字节对拍**"原则
- 🔌 **新语言移植**：请附**机制可移植性分析**（哪些能抄、哪些要重做）

**不接受**：

- ❌ 声称"提高强度"但没有实测数据的 PR
- ❌ 引入未经审计的第三方密码学实现
- ❌ 移除"诚实边界"章节的文档改动

## 六、安全问题报告

如果你发现了**能绕过保护**的方法：

1. **请勿公开披露**
2. 通过仓库的 Security Advisory 私下报告
3. 附最小复现

我们会：

- 确认后**优先修复**
- 在 `docs/PITFALLS.md` 记录（用"实测打脸"的口吻，不带攻击细节）
- 在 Release Notes 致谢

> 我们**欢迎**被攻破——**一份诚实的 "实测打脸清单" 比一份虚假的 "无法破解" 承诺有价值得多。**
