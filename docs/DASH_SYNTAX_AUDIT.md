# dash 语法审计（DASH_SYNTAX_AUDIT）

> r23 实测报告。**修正并细化了 `GENERALIZATION_FEASIBILITY.md` 对第 2 层的估计。**
>
> 方法：生成真实 V6 产物 → 用最小 `sed` 替换 → 丢给 dash 跑 → 看报错列表如何变化；
> 同时逆向产物骨架在生成器中的源码位置，逐构造统计。
> 所有数据均为本机复现，非推测。

---

## 一、两条结论

**① 好消息：数组下标不用改。** dash 原生支持 `${a[0]}` 这种**位置参数下标**语法，而我们的产物**恰好就运行在那个模式上**。原估计"数组下标访问遍布解释器、要全部改写"**不成立**。

**② 坏消息：但挂点比原来认为的多。** 产物**主解释器循环**里有 **6 处 `<<<`（here-string）和 4 处 `<(...)`（进程替换）**，而 **dash 完全没有进程替换**（语法级缺失，无法降级绕过）。这 4 处是真正的硬点。

原报告只列了 `<<<` 的性能损失，**漏掉了 `<(...)` 这一项**。这是本次审计最重要的修正。

## 二、实验一：`declare -a` 到底有多硬

### 2.1 原始产物在 dash 下的报错

```
$ dash prod_test.sh
prod_test.sh: 2: declare: not found
prod_test.sh: 2: _Rc[0]=ueU37...:70737b7dcf17c66f: not found
prod_test.sh: 2: declare: not found
prod_test.sh: 2: _lQ[0]=nUdtm3...:7908962f8a882828: not found
...
```

两类报错：

| 报错 | 根因 | 次数 |
|---|---|---|
| `declare: not found` | bash 内建，dash 没有 | 4 |
| `_X[N]=...: not found` | 上一行失败后赋值被当**命令名**查 PATH | 每次赋值 |

### 2.2 分语义实测：dash 的数组能力边界

```bash
# ① 真数组：声明 + 下标赋值 + 下标展开
$ dash -c 'X=; X[0]=a; X[1]=b; echo "${#X[@]}"'
dash: 1: X[0]=a: not found
dash: 1: Bad substitution                  ← ❌ 无真数组

# ② 位置参数下标（关键）
$ dash -c 'set -- a b c; echo ${2}'
b                                          ← ✅ 原生支持
```

**② 是分水岭。** dash 里 `${2}` 就是 `$2`；`${_c[$_p]}` 在 `set --` 模式下的语义**完全等价**于位置参数访问。

### 2.3 最小替换实验

```bash
sed 's/declare -a \([A-Za-z_][A-Za-z0-9_]*\)/\1=/g' prod_test.sh > prod_posix.sh
```

| 项目 | 替换前 | 替换后 |
|---|---|---|
| `declare: not found` | 4 处 | ✅ **消失** |
| `Bad substitution` | 多次 | ✅ **消失** |
| `_Rc[0]=...: not found` | 有 | **仍有**（见 2.4） |

### 2.4 剩下的报错不是数组问题

`_Rc[0]=v` 在 `set --` 执行**之前**无处可归（dash 无真数组）。这是**降级顺序**问题，不是能力缺失 —— 完整方案是"把 `_Rc[0]=v` 也改成攒字符串，再 `set --`"。

产物骨架的实际执行顺序：

```
1. declare -a _Rc; _Rc[0]="..."; ...      ← 现在这步通了
2. 中间若干步
3. set -- ${_Rc[@]}                        ← 数组降级为位置参数
4. ${_c[$_p]} 基于 $1/$2/... 全部可用
```

## 三、实验二：产物主循环的完整构造清单（本次核心修正）

产物骨架源码在 `generate_output_v6()`（`2197` 行起），其中：

- 数组声明模板：`2239/2246/2275/2279`（4 处）
- **主解释器循环**：`1113`–`1290` 区间（含 `_am()` 密钥推进在 `1089`）

### 3.1 主循环里 dash 不支持的构造统计

对 `1113`–`1300` 区间逐构造统计：

| 构造 | 次数 | dash 支持？ | 处置 |
|---|---|---|---|
| `<<<` here-string | **6** | ❌ 语法错 | → `printf … \| read` / 临时文件 |
| `<(…)` **进程替换** | **4** | ❌ **语法错，最硬** | → 临时文件（性能有损） |
| `EPOCHREALTIME` | 2 | ❌ 空值 | → `date +%s%N` 或去掉超时检测 |
| `${arr[@]}` 展开 | 3 | ❌ | → `"$@"` / `"$1 $2 …"` |
| `[[ ]]` | 0 | — | 不在主循环 |
| `declare` | 0 | — | 只在骨架开头 |
| `read -a` | 0 | — | 单独出现，非主循环 |

### 3.2 `<(…)` 那 4 处的真实代码

```bash
case "$_pp" in
    0) builtin eval "$_code" ;;
    1) builtin source /dev/fd/9 9<<< "$_code" ;;
    *) builtin source <(printf '%s' "$_code") ;;     ← 进程替换
esac
```

**分三档**（`_pp` 由环境探测决定），这意味着：

1. **档位 0（`builtin eval`）已经是纯 POSIX** —— 无需改动。
2. 档位 1 的 `9<<<` 就是那 6 处 here-string 之一。
3. 档位 2 的 `<(...)` 是进程替换。

> **关键观察**：`_pp` 是个**运行期才确定**的分派变量（探测 trace 开关、TracerPid、`LD_PRELOAD`、耗时等）。也就是说 —— **产物本来就有"退化为纯 POSIX 路径"的机制**，只是没有针对目标 shell 静态选择。
>
> 对 dash 支持而言，最省力的做法可能是：**让 `_pp` 在 dash 下直接锁死为 0**，从而**完全绕过 `<<<` 和 `<(…)`**。这比逐处改写 is 一个小得多的改动。**（待验证：档位 0 是否在所有场景语义等价）**

## 四、唯一**无法**通融的缺失：并发原语

实测 dash 的硬缺失（语法级，无法降级绕过）：

| 构造 | dash 结果 |
|---|---|
| `coproc A { ...; }` | `Syntax error: "}" unexpected` |
| `cat <(echo hi)` | `Syntax error: "(" unexpected` |
| `$(</tmp/file)` | 返回空串 |
| `local a=1`（函数内） | ✅ **支持** |

**审计结果：产物与生成器均不使用并发原语**（`coproc` 0 次、`wait` 0 次、`mkfifo` 0 次、后台 `&` 0 次）。

> 生成器自身有 4 处 `<(`（`1131/1160/1248/1276`），但**均在产物模板内**，属于上面的"档位 2"分支，不是独立并发需求。

**结论：并发不构成障碍。** 交付本报告时唯一担心的因素已排除。

## 五、修正后的第 2 层清单

| # | 构造 | 位置 | 改法 | 难度 |
|---|---|---|---|---|
| 1 | `declare -a _Rc` / `_lQ` | `2239/2246/2275/2279` | → `_Rc=` | ⭐ 一行 sed |
| 2 | `_X[0]=v` 按行赋值 | 骨架 | 攒字符串再 `set --` | ⭐⭐ |
| 3 | `${_c[$_p]}` 下标读 | 主循环 | ✅ **不用改** | — |
| 4 | `${#_c[@]}` | 主循环 | → `$#` | ⭐ |
| 5 | `"${_ial[@]}"` | 主循环 | → `"$@"` | ⭐ |
| 6 | `<<<` × 6 | 主循环 | → `printf\|read`，**或锁 `_pp=0` 整段绕过** | ⭐⭐ |
| 7 | `<(…)` × 4 | 主循环 | → 临时文件，**或锁 `_pp=0` 整段绕过** | ⭐⭐ |
| 8 | `EPOCHREALTIME` × 2 | `_am()` + 主循环 | → `date +%s%N` 或去掉 | ⭐ |
| 9 | `[[ "$err" != *…* ]]` | `2504` | → `case` | ⭐ |
| 10 | `[[ $- == *x* ]]` | `1891/1895` | → `case $- in *x*)` | ⭐ |

**全部是可枚举的有限构造集**，没有"遍布解释器"的东西。这正对应 `PRIOR_ART_REVIEW.md` 第 2.9 节的教训：*不要做通用 bash→sh 转译器，只降级我们自己产物里出现的那个有限构造集*。

## 六、对路线的影响

- **好消息**：第 2 层从"改写整个解释器的数组访问"降为"**4 行声明 + 约 15 处构造**"。
- **坏消息**：其中有 **10 处（6 个 `<<<` + 4 个 `<(…)`）集中在主循环**，且 `<(…)` 在 dash 里**没有原生替代** —— 只能走临时文件，有性能代价。
- **可能的捷径**：产物**已有三档 `_pp` 分派**，其中档位 0 就是纯 POSIX。**若能让 dash 下锁死档位 0，则 `<<<` 和 `<(…)` 全部绕过，第 2 层只剩约 5 处零星改动。**

> **止损点（不变）**：生成一个 dash 产物，看它**能否跑通第一个块**。
> 现在的判断是**大概率能**，但成本集中在主循环的那 10 处，需先验证"档位 0 捷径"。

**下一步（按性价比）**：

1. **验证 `_pp` 档位 0 的语义等价性** —— 这是能否把工作量再压一个数量级的关键。
2. **写跨 shell 跑通检查器**（`PRIOR_ART_REVIEW.md` 第 4.2 节 `crossrun` 闸门）—— 同时是审计与验收工具。
3. 再决定是否正式开工档位 2。
