# 心路历程：从"加密一下"到 v6

> 这份文档记录 ShellVMP 从第一行代码到 v6 的完整试错过程。
>
> **为什么值得写下来**：市面上讲"怎么做混淆"的资料很多，讲"**为什么这么做会失败**"的几乎没有。而保护这种事，**失败的方式比成功的方式更有信息量**——因为攻击者只需要找到一个漏洞，你需要堵住所有。
>
> 下面每一节都是一个"我以为这样就行了 → 实测被打脸 → 改成这样"的循环。**附实测数据**。

## 第 0 版：加密一下不就完了？

最开始的想法非常朴素：**把脚本内容加密，运行时解密再 `eval`**。

```bash
#!/usr/bin/env bash
eval "$(openssl enc -d -aes-256-cbc -k "$KEY" -in payload.enc)"
```

三分钟写完，跑通了，很得意。

然后自己当攻击者试了一下：

```bash
# 攻击者的第一条命令
strings prod.sh | grep -i key
```

**密钥就在同一行**。整个方案的信息论强度约等于零——密码学保护的是"没有密钥的人"，而这里密钥是公开的。

> **教训 0**：**密钥和被加密的数据放在一起，等于没加密。** 这句话是后面所有设计的起点。

## v1-v2：base64 与 XOR 的幻灭

第一轮真正开始"做混淆"。思路是**让代码看起来不像代码**。

```bash
# v1：整体 base64
eval "$(echo 'IyEvdXNyL2Jpbi9lbnYgYmFzaAplY2hv...' | base64 -d)"

# v2：逐行 XOR 一个固定 key
```

**实测被秒破**，两个原因：

1. **base64** 根本不是加密，`base64 -d` 一条命令就出来。
2. **XOR** 看起来好一点，但只要攻击者有**任何一段已知明文**（脚本开头总是 `#!/usr/bin/env bash`），就能直接推出密钥流，然后**全程解出**。

我用了一个当时觉得很妙的技巧：**每条命令单独 XOR 一个不同的 key**（key 由行号派生）。结果：

```
攻击者视角：
1. 猜出第一行明文（谁都知道）→ 推出 key1
2. key 由行号派生 → 整个 key 序列全部可推
3. 全部解出
```

**单字节 XOR + 密钥可由行号派生 = 已知明文攻击一步到位。**

> **教训 1**：**"每条用不同密钥"不是安全性，只要密钥之间有关联。** 密钥派生函数必须是密码学安全的（单向、雪崩效应），不能是"能猜出来的公式"。
>
> **教训 2**：**已知明文攻击是脚本混淆的头号杀手**——因为脚本的开头、变量名、常见命令都**高度可预测**。任何流密码都必须保证**已知明文不能推出密钥流的其他部分**。

## v3：上 AES，然后发现密钥还在

既然 XOR 顶不住，就上真的密码学。

```bash
CRYPTO_MODE=aes   # openssl AES-256-CTR + PBKDF2
```

本次改进：

| 改进 | 理由 |
|---|---|
| 指令/数据块改用 **AES-256-CTR**（逐项独立密钥流） | 已知明文只能推出**密钥流片段**，对 256bit 密钥零信息 |
| 一层壳改 **gzip + PBKDF2-AES-256-CTR**（sha512，高迭代） | 拉高攻击者枚举成本 |
| **骨架自哈希 `H_skel`** 掺入一层口令 P1 | 改骨架任何一字节都必须完整重放 PBKDF2，插桩成本叠加一个量级 |
| 工具路径**编译期绑定绝对路径** | 免疫 PATH 劫持型的密钥窃听 |
| **指令批量打包**（`INST_BATCH=16`） | 运行期 openssl 进程数降到 1/16 |

跑通后我满怀信心地自测：

```bash
strings prod.sh | grep -i -E 'key|pass'
# → 果然没有密钥明文
```

**但是**——产物还能跑，那密钥在哪？

**答案是：在代码里算出来的。**

```bash
# 简化示意
K=$(echo "$(hostname)$(date +%s)$(cat /proc/cpuinfo)" | sha256sum)
```

密钥是**运行期从环境算出来的**。攻击者只需**读一遍你的 shell 代码**，就能照着算一遍——**因为解密逻辑本身是明文的**。

> **教训 3**：**"密钥不写在文件里"和"密钥不暴露"是两回事。** 只要**派生算法**是明文的，攻击者就能**自己跑一遍算法**得到密钥。这是 **Kerckhoffs 原则的实战翻车**。
>
> **教训 4（关键）**：**当解密器本身是明文时，一切加密都是纸糊的。** 这直接指向后来两条路线：要么**保护解密器**（V7 的魔改+VMP 路线），要么**让密钥依赖不可复现的东西**（v4 的 passkey）。

这一版还有个副产品：**环境熵**（`KEY_ENTROPY`）——把 `uname` 输出、Android 版本掺进密钥。当时以为是安全特性，后来发现它**绑定了设备**，分发给版本混杂的设备会集体打不开。**功能正确 ≠ 产品可用**。

## v4：passkey 密钥分离——第一次理论上的突破

v3 的死结是"解密算法明文 → 密钥可复现"。破解它的思路只有一条：

> **让密钥依赖一个攻击者拿不到的东西。**

而在纯静态文件里，唯一"攻击者拿不到"的东西是——**用户脑子里的口令**。

于是有了 **密钥分离模式**（`PASSKEY_MODE=1`）：

```
编译期:
  生成随机主密钥 M（强随机，如 256bit）
  用 M 派生一层口令 P1 → 加密脚本
  用 passkey 包裹 M（PBKDF2，可多个 passkey 各自包裹）
  ← M 本身【绝不写入产物】

运行期:
  用户输入 passkey → 解包裹得到 M → 推得 P1 → 解密脚本
```

**信息论上的意义**：攻击者拿到产物后，**产物里不包含解密所需的全部信息**。没有 passkey，即使完全理解你的算法，也无法解密——**这不是"算力问题"，是"信息缺失"**。

第一次测试通过时，是有点激动的。因为这是**第一个理论上成立的防线**。

但立刻遇到新的工程问题：

| 问题 | 表现 | 解法 |
|---|---|---|
| **弱口令** | 攻击者离线爆破（每次尝试一次 PBKDF2） | `UNWRAP_ITER` 可调（默认 10000，自定义弱口令建议 300000） |
| **`builtin` 模式 KDF 强度倒挂** | 攻击者用原生语言重实现 KDF 每轮仅 ~1µs | 明确警告：builtin 模式**务必用随机长密钥** |
| **多密钥管理** | 想给不同用户发不同密钥 | `PASSKEY_COUNT` / `PASSKEY_CUSTOM`（每个 passkey 独立包裹 M） |

> **教训 5**：**"信息论安全"只在"信息真的缺失"时成立。** passkey 模式是唯一做到这点的设计——**其他所有层，本质上都是在"提高成本"，而不是"消除可能"**。
>
> 这个认知后来变成了整个项目的定调：**诚实地说清每一层是"消除"还是"提高成本"**。

## v5：完整性保护与"解不开就别解"

v4 之后，我做了一件当时觉得多余、后来证明极其重要的事：**当攻击者来试篡改**。

攻击场景很朴素：**改一个字节会怎样？**

实测结果让我冷汗直流：

```
篡改密文的一个字节
→ 解密出来是"乱码"
→ 但脚本还是把它 eval 了
→ 报了一堆莫名其妙的语法错误
→ 最坏情况：乱码碰巧是合法语法，执行了错误逻辑
```

**"解密密文被 `eval`"是一个真实存在的窗口。**

于是 v5 引入 **encrypt-then-MAC**：

```
每个密文项 = 密文 + 16 字节标签
标签 = HMAC-SHA256(密钥, 密文)      # aes 模式
标签 = sha512 三明治                 # builtin 模式

_f() {
    先验签
    ├─ 失败 → exit 1（干净拒绝，绝不 eval 乱码）
    └─ 成功 → 解密
}
```

**"解不开就别解"**——这个哲学后来贯穿整个项目：

- V7 的 `blob_verify` 失败 → `die(114)`，**一行用户代码都没跑**
- V6 的一致性自校验失败 → 静默乱码，但**绝不半解**

> **教训 6**：**加密系统必须有"完整性"这一维。** 只有机密性（加密）没有完整性（MAC），等于给攻击者留了一个"任意篡改"的接口——而乱码被解释执行是**最危险**的失败形态（可能静默执行错误逻辑）。

## v6：链式动态跳跃块解密

v5 是一个"静态加密"系统——**每个块独立加密**。这带来最后一个致命弱点：

> **攻击者可以逐块独立分析。** 拿到第 5 块的密文，可以单独研究它，不需要理解第 1-4 块。

v6 的核心思想：**让每个块的解密依赖前面所有块的执行结果**。

### v6 的三个核心机制

**① 执行状态绑链（`_s` 链）**

每个块的解密密钥掺入**前一个块的实际执行状态**：

```bash
# 块 i 的 _s 由三个真实执行状态构成（六种排列随机选一）
_s = f( rt, rc, pp )
#   rt = $_   （上一条命令的最后一个参数）
#   rc = $?   （上一条命令的退出码）
#   pp        （执行路径：0=eval / 1=fd here-string / 2=process-sub）
```

**这意味着**：攻击者不能用"静态推导"解密第 i 块——必须**真实执行**第 i-1 块，并且**得到相同的 `$?` 和 `$_`**。

**② 跳跃式密钥链（`JUMP_DIST=7`）**

第 N 块额外掺入**第 N-7 块的密钥链值**：

```bash
if [ "$i" -ge "$JUMP_DIST" ]; then
    jump_ck="${CK_HISTORY[$((i - JUMP_DIST))]:-}"
fi
```

**为什么要跳跃而不是线性**：如果只依赖"前一块"，攻击者从中间 dump 出来后**可以向后重建**（只要他知道当前状态）。跳跃引用让**中间起点的向后重建也失效**——必须**从头完整执行**。

**③ 批级自修改（`_am`）**

每处理一批指令，就用 LCG 推进随机数状态，**重新加密整批指令**：

```bash
_am() {
    _rs = (_rs * 1103515245 + 12345) & 0x7fffffff
    RANDOM=$_rs                          # 重播种 bash 的 RANDOM
    _ra=$RANDOM; _rb=$RANDOM             # 消费两次
    _mk = sha512(_mk + _p + _ra + _rb)[0:16]
    _c[$_p] = $(_e "$_b" "$_mk" "$_p")   # 重加密整批
}
```

**这意味着**：攻击者 dump 出来的内存快照**是一次性的**——即使拿到了某一刻的密钥，下一秒它就变了。

### 代价：两个"看起来能抄实则要重做"的坑

**坑 1：`$RANDOM` 状态机必须完整复现**

因为 bash 的 `$RANDOM` 不是一个简单的 LCG——它是 **Park-Miller Schrage 法** + **去重循环**：

```c
// bash 5.1+ lib/sh/random.c 的真实行为
brand: ((rseed >> 16) ^ (rseed & 65535)) & 32767
do { rv = brand(); } while (rv == last);   // ← 这个去重循环极易漏
```

**为什么必须复现**：编译期要**模拟执行**用户代码来捕获执行状态，模拟器里的 `$RANDOM` 序列必须与运行期**逐字节一致**。差一个数，整个密钥链就分叉。

> 我为此把 bash 的 `random.c` 完整读了一遍，写出状态机模拟器。**换语言时，自带一个三行 LCG 更省事。**

**坑 2：编译期与运行期必须同源**

V6 的编译期需要"真正跑一遍用户代码"来生成 `_s` 链。如果运行期跑在**魔改 bash** 上，编译期也**必须用同一个魔改 bash**——否则 `$?`、`$_` 的行为可能不同。

解法：`V7_SIM_BASH` 环境变量 + `V7_SIM_REQUIRED` **fail-closed**（宁可构建失败，不出坏产物）。

### v6 的伴生机制（都是被攻击逼出来的）

| 机制 | 起因 |
|---|---|
| **不透明谓词**（恒真/恒假的算术式） | 防止攻击者用简单的模式匹配识别块结构。只用 `+ - *`，避开 `==`/`%`（不同 awk 行为不一致） |
| **诱饵块 vs 垃圾块** | 诱饵走假谓词（零执行）；垃圾块**真实 eval**、参与密钥链 → AI 重放时一个都跳不过去 |
| **契约名随机化** | 每次构建重命名所有内部变量，攻击者无法写固定规则 |
| **完整性三重自校验** | 骨架、密文、字面量三处归一化比对，改任何一处都失败 |

### v6 最大的教训：静默算错

v6 的开发过程中，**最难的 bug 都不是"报错"，而是"静默算错"**：

| 症状 | 根因 | 排查耗时 |
|---|---|---|
| 产物 rc=0、输出截断、无报错 | 随机变量名**撞名**（25 个变量从 62² 空间抽取，撞名概率 ~8%）→ 某块 `rt_name` 撞上循环计数变量 → 计数被覆盖成信标串 → `[ p -lt n ]` 报错 → **VM 静默提前退出** | 三天 |
| 产物解出来是 base64 垃圾 | 撞上链变量 → 密钥链分叉 | 同上 |
| `munmap_chunk(): invalid pointer` | hook 返回 static 表指针 → bash 词法器 `FREE` 了非堆地址 | 两天 |
| 脚本"跑几条就停" | 宿主 `errexit`（脚本第 7 行裸 `false`） | 三轮 |
| 脚本静默 exit、零提示 | 脚本内 `set -x`/改 `PS4` 命中反调试指纹 → 主密钥污染 | 一周 |

**这些 bug 的共同点**：**没有崩溃、没有报错，只是悄悄输出了错误结果。**

> **教训 8**：**在混淆系统里，"能跑通"和"结果正确"是两件完全不同的事。** 唯一可靠的验证是**逐字节对拍**（原脚本 vs 产物）。

这个教训直接催生了两件工具：
- `tools/v6_lint.py` —— 混淆**前**静态检查（把 `errexit`/`set -x`/`PS4` 这些杀手揪出来）
- `tools/v6_pm_diag.sh` —— 运行期逐项诊断 6 个指纹条件

## v7 之后：从"混淆脚本"到"魔改解释器"

v6 已经把"脚本层"做到了极限。但有一个根本问题解决不了：

> **无论怎么混淆，最终都要把明文交给 bash `eval`。那一刻，明文是完整的。**

于是有了 V7 的两条路线：

**路线 A：外挂 ELF 加载器**——父进程解密、子进程执行，明文走 pipe **即写即抹**。
**路线 B：魔改解释器内嵌**——把解密逻辑做进 bash 自己，**单进程**，明文**从不完整出现在内存里**。

**"能单进程就单进程"** 是这里最重要的结论——多进程的进程间通信**必然**是可攻击的明文窗口。

V7 还带来了一个反直觉的收获：**"检测到入侵时，不要报警，要破坏"**。

```bash
# 环境指纹命中时，不 exit，而是把密钥链毒化
[ "$_pm" = 1 ] || _mk="${_mk}q"    # ← 静默破坏，产物解出一堆垃圾
```

**报警可绕，破坏不可绕。** 攻击者看到进程退出了，会去 patch 检测逻辑；但如果产物"正常跑完但结果是错的"，他会以为是自己的方法错了——**这才是真正的防御**。

### V7 的实测打脸清单

有些"理所当然"的防护，实测**完全不成立**：

| 我以为 | 实测 |
|---|---|
| `PROT_NONE` 能拦住 `/proc/pid/mem` 读取 | ❌ 拦不住。内核走 `get_user_pages`，**不检查页表权限** |
| `unset` 能擦除内存 | ❌ 不擦。密文留下 5 份副本、明文留下 8 份递减前缀 |
| "窗口式保护"有用（只在解密瞬间短暂暴露） | ❌ 8 线程高频轮询，**命中率 99.9995%** |
| `free` 之后内存就干净了 | ❌ chunk 会被复用，擦过的零被覆盖成调用方数据 |

**这四条后来成了 skill 里最常被引用的"别做梦"清单。**

## 贯穿全程的五条教训

### 1. 分清"消除可能"和"提高成本"

| 层次 | 性质 |
|---|---|
| 密钥分离（passkey） | **消除可能**（信息论） |
| 一切其他手段 | **提高成本** |

产品说明里必须写清哪层是哪层。**混淆永远不会"无法破解"。**

### 2. 攻击者只需要一个漏洞

你做 10 层保护，攻击者找到最弱的那层就够了。**整体强度 ≈ 最弱组件。**

### 3. 静默算错比崩溃危险

崩溃你会去查；静默算错你会**交付一个坏产物**。所以：**逐字节对拍是唯一可靠的验证**。

### 4. 检测到入侵要破坏，不要报警

报警是一种"可以被 patch 掉的行为"。**让攻击者的工具"正常跑但结果是错的"，比让它"明显失败"有效得多。**

### 5. 诚实是最好的策略

**"挡不住 root"就说挡不住 root。** 虚假的安全承诺会让使用者做出错误的风险判断——这比不保护更糟。
