## 一、zsh 兼容 —— 暂不做

**决策时间**：2026-09-14（r23 靶子调研后）
**决策**：**不把 zsh 列入兼容目标**，从通用化路线中移除。

### 为什么不做

核心论据是**"shell 使用率"有三种含义，混起来会得出错误结论**：

| 含义 | bash | zsh | mksh | dash |
|---|---|---|---|---|
| ① **交互 shell**（人打命令用的） | 31% | **62%** | (Android 全部) | ~0% |
| ② **脚本 shebang**（`#!/bin/bash`） | **绝大多数** | ~0% | ~0% | 少量 |
| ③ **系统 `/bin/sh`** | — | — | **Android** | **Debian/Ubuntu** |

ShellVMP 兼容的是 **② 和 ③** —— 即**脚本运行环境**。而 zsh 在这个维度：

- **② 脚本 shebang ≈ 0%**：zsh 用户写脚本时仍用 bash 或 POSIX sh。zsh 的专有语法（1-based 数组、扩展 glob、参数展开 flag）写出来的脚本**无法在别的 shell 跑**，所以社区共识就是"要可移植就写 bash/POSIX"（Google Shell Style Guide 强制 bash）。
- **③ 系统 `/bin/sh` 从来不是 zsh**：没有任何主流发行版把 zsh 作为 `/bin/sh`。

反向证据（zsh 在 ① 确实强势，但与我们无关）：

- **JetBrains 2025**：自定义 shell 的开发者中 **62% 用 zsh 交互**、31% bash、7% fish。
- **CNCF 2025**：**94% 的 CI/CD 流水线用 bash**；"zsh 在生产基础设施中的使用率基本为零"。
- Apple 自 2019 起把 zsh 作为 macOS 默认 —— 但这影响的是**开发者工作站的交互体验**，不是脚本分发。

### 追加理由：技术上也不划算

即便忽略使用率，zsh 的兼容成本也不低：

- zsh **数组 1-based**（bash 0-based），下标语义整体偏移。
- zsh **默认不做单词分割**（`SH_WORD_SPLIT` 关闭），这是与 bash 最深的语义分歧之一。
- zsh 的 `emulate` **改 options 不改解析器**（实测 `emulate bash` 不存在，静默退化为 `sh`，且完全不改变 `$RANDOM` 序列），指望不上。
- 结果是：兼容 zsh 既不能像 mksh 那样"只差 4 个构造"，也不能像 dash 那样"降级到 POSIX 子集即可"，而是要处理一套**与 bash 平行的语义体系**。

### 重启条件（满足任一即重新评估）

1. **有真实用户明确提出** zsh 场景（例如"我的用户全是 macOS 开发者，产品要跑在他们的默认 shell 里"）。
2. **mksh + dash 都已完成**，且通用化框架已稳定到"加一个 shell 后端"是低成本操作。
3. zsh 官方或社区推出**可靠的 bash 语义兼容层**（届时见 [`PRIOR_ART_REVIEW.md`](PRIOR_ART_REVIEW.md)，需重新调研）。

> **注意**：本决策**不影响** `tools/interp_compat/` 的思路 —— 那套"给目标 shell 装 bash 语义 hook"的方法论对 zsh 同样适用（`$RANDOM` 的 hook 换个宿主即可）。真要做 zsh 时，**从这套现成机制出发**，不要从零开始。

## 二、≥10 块脚本的静默提前退出（既有缺陷，与 shell 无关）

**发现时间**：2026-09-14（mksh 兼容改造期间的回归验证中偶然暴露）
**状态**：**待排查**（不是 mksh 引入的，也不是本轮引入的）

### 现象

较长的脚本（实测 11–16 个块）混淆后运行，VM 会在某个中间块处**静默 `exit 1`**：
无任何报错输出、rc=1、stdout 在中断点被截断。

**关键特征：bash 与 mksh 在完全相同的位置失败。** 这排除了"shell 兼容"这个方向 —— 是密钥链或块表本身的既有 bug。

### 已确认的事实

1. **不是本轮改动引入的。** 用改动前的生成器快照（`gen.pre_rt.bak`）在同一脚本上复测：
   - 改动前：bash 输出 `5 / 3 / 4` 行（不稳定），mksh **`0 / 0 / 0`**
   - 改动后：bash 输出 `4 / 3 / 3` 行，mksh **与 bash 逐行一致**
   - → 本轮改动**没有让 bash 变差**，反而让 mksh 从"跑不起来"变成"与 bash 一致"
2. **产物本身是确定的。** 同一份产物重复运行 100% 复现同一失败点。失败点随**重新生成**而变（生成器随机化）。
3. **失败点是解析期 `exit 1`，不是执行期报错。** 去掉生成器里所有的 `2>/dev/null` 后仍无任何错误输出 → 是解释器里显式的 `[ -n "$_code" ] || exit 1`（解密失败路径）。
4. **已排除的构造**（逐个单独测均通过，bash/mksh/dash 三方一致）：
   `mkdir -p`、`case … esac`、`while` 循环、`for` 循环、函数定义 + 调用、
   `if`/`fi`、`$?` 引用、`$_` 引用、以及上述构造的两两组合。

### 已缩小的范围

一个稳定复现的最小样本（11 块）特征：

```sh
# 前置：APP/VER/ROOT 赋值、log() 定义、check_env() 定义
log "starting"
if check_env "sh cat"; then log "env ok"; else log "env missing"; fi   # ← 通过
mkdir -p "$ROOT"                                                        # ← 通过
log "mk ok"                                                             # ← 通过
case "$VER" in
    2.*) log "major 2 branch" ;;    # ← 有时到这一步，有时到不了
    *)   log "other branch" ;;
esac
log "case ok"                       # ← 未到达
```

去掉 `check_env` 的定义后就不再复现 —— 但 `check_env` 单独测完全正常。
**所以是"函数定义块"与"后续块"的某种交互**，怀疑落在：

- `_ck` 的"跳跃式链绑定"（第 N 块掺入第 N-7 块的 `_ck`，代码注释提到 r10 加入）
- 或块表 `_Da` 在长链上的某次 `_0E` 回写

### 下一步

从 `CEXEC` 指令流入手，dump 出某个块解出的 `_code` 为空的具体是哪一块，
再对比编译期 `sim.sh` 与运行期在该块上的 `s_in` / `ck` 输入。**注意**：
产物改一个字节就会触发 `_hs` 自毁，所以只能在生成器里临时插桩。

### 为什么记在这里而不是马上修

本轮的目标是 **mksh 兼容（P0）**，已达成。这个缺陷**与 shell 选择完全正交**：
在 bash 上它同样存在，也不属于通用化路线。按计划的止损原则，
应当作为独立条目排期，而不是挂在 mksh 工作线上越滚越大。
