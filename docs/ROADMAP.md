## 二、已知限制（诚实清单）

### 2.1 V7-ISA 绑定 bash 5.2

**这是最重要的限制。**

V7-ISA 的插桩点依赖具体源码结构：

```
bash 5.2 源码：
  execute_cmd.c   execute_simple_command()    ← L1/L2 插桩点
  y.tab.c         CHECK_FOR_RESERVED_WORD 宏  ← L3 插桩点
  variables.c     find_variable()             ← L4 插桩点
  shell.c         shell_initialize()          ← 接管安装点
```

bash 主版本升级时，这些位置可能变化，需要**重新校准**。

**风险评估**：

| 因素 | 判断 |
|---|---|
| bash 主版本发布频率 | 约 2-3 年一版，**短期风险低** |
| 插桩点稳定性 | `execute_simple_command` 等是核心函数，**不太可能大改** |
| 宏 `CHECK_FOR_RESERVED_WORD` | 词法层核心宏，**稳定** |
| 应对成本 | 重新校准约 1-2 天（有文档指导） |

**结论**：**这层是"可移植性最弱、但价值最高"的部分**，短期（3-5 年）风险可接受。

### 2.4 V6 安卓门控的退出码歧义

**V6 门控拒绝时维持 `exit 1`，不改 `113`**（已裁决）。

理由：
- 任何退出码都可能被用户脚本自然产生或故意占用（脚本里写 `exit 113` 与门控拒绝**无法区分**）
- 换码只能降低概率，**不能根除歧义**
- 且门控拒绝在表现上与"用户脚本自身失败"一致，恰好符合 V6「不泄露被保护信息」的隐蔽性设计

**可靠的区分手段**：对照运行（先跑原脚本记录 rc 与输出，与产物比对）。

**对比**：V7 C 层保留 `die(113)` 不受此影响——V7 在解密前就 die，用户脚本一行未跑，rc 只可能来自 V7 自身，且带 stderr 消息，歧义窗口小。

## 四、跨语言可行性（简要结论）

> 判据：**这条机制之所以有效，是因为"攻击者的行为模式"，还是因为"语言特性"？**
> 前者通用可抄，后者要重找等价物。

| 语言 | 适配度 | 说明 |
|---|---|---|
| **bash** | ✅ 原生 | — |
| **Lua** | ✅ **最佳移植目标** | 官方就是解释器；源码可编译（魔改路线完全走得通）；不依赖外部编译链 |
| **PHP** | ✅ 好 | 解释器型；`auto_prepend_file` 对应 `BASH_ENV` |
| **JS** | ✅ 好 | 解释器型；但有 JIT，明文窗口问题更复杂 |
| **Python** | ⚠️ 中 | `.pyc` 字节码有额外坑；`sitecustomize.py` 对应 `BASH_ENV` |
| **Dart/Flutter** | ❌ **不适用** | Release 是 **AOT**（无解释器、无字节码下发）→ **"明文窗口"前提不成立** |

**Dart/Flutter 的具体问题**（详见 `docs/` 相关分析）：

```
Flutter release 产物：
  libapp.so = 纯 AOT 机器码（_kDartIsolateSnapshotInstructions）
  没有 Dart VM 解释器，没有 .dill 字节码
  → "解释器必须读懂代码 → 攻击者也能" 这个前提不成立

```

若要硬做，只有"自己写 Dart 子集运行时"（`dart_eval` 路线），**投入产出比极差**。

## 五、通用化路线（跨 shell 保护）

> 完整分析见 [`GENERALIZATION_FEASIBILITY.md`](GENERALIZATION_FEASIBILITY.md)（含实测数据与功能剥离表）。

**简要结论**：跨 shell **不是语法问题，是密钥链把解释器语义烧进了密文**。

- 密钥链 7 个因子里，`SEED`/`FP`/`DV`/`IH` **4 项与 shell 无关**，`$-`/`VERSINFO[0]`/`len(VERSINFO[])` **3 项是"注入常量"的机械操作**。
- 真正的硬骨头是 `_am()` 里的 **`$RANDOM` 状态机** —— 编译期 `sim_random_next()` 从零复刻了 glibc `random()`，与 bash 逐比特对齐。dash **没有 `$RANDOM`**（实测得字面量），zsh 算法不同且受 `.zshrc` 影响。
- **跨 shell 与"必须模拟执行"是同一枚硬币的两面**：要跨 shell，就得剥离最高强度的三层绑链（`_am` 推进 / `$_`·`$?` 绑链 / ISA 令牌化）。

| 档位 | 内容 | 工作量 | 状态 |
|---|---|---|---|
| **P0** | 产品化：`V7_SELF=1` 转正 + 输入面体检工具 + README 边界 | 半天 | ⭐⭐⭐⭐⭐ 直击真实痛点 |
| **P0b** | **mksh-only PoC（Android 真靶子）** | 1-2 天 | ✅ **已完成**（2026-09-14） |
| P2 | dash 子集 PoC（成本最高，服务器场景） | 3-5 天 | ⭐⭐ 边际收益有限；**需先做数组模拟** |
| P5 | 完整跨 shell（mksh+dash+ash） | 2-4 周 | ⭐ 不划算（zsh 不做） |

> **P0b 完成详情**（2026-09-14）：产物在 **mksh 下与 bash 输出逐字节一致**（8 轮独立生成 8/8 通过）。
> 验收门禁：[`tools/sh_compat_check.sh`](../tools/sh_compat_check.sh)。
> 改动清单与"计划外四大真凶"（`$RANDOM` / `$-` / `$_` / `read -a`）见
> [`SHELL_TARGETS.md`](SHELL_TARGETS.md) 第九节，踩坑记录见 [`PITFALLS.md`](PITFALLS.md) 第八节。
>
> **P2 定位修正**：dash **完全没有数组**（`_mx=; _mx[0]="abc"` → `Bad substitution`），
> 所以 mksh 用的 `declare -a X` → `X=` 这一招对 dash **不够**，需要额外的标量模拟层。

**关键认知**：用户感知的"只能保护 bash"里，约 **80% 已经解决** —— `V7_SELF=1` 内嵌静态 bash 让产物跨平台（aarch64 bionic/musl + x86_64 全覆盖），且 `v7_wrap.sh` 本身就是 `#!/bin/sh`（外层载体已是纯 POSIX）。缺的是"写成默认路径 + 把边界说诚实"。

### 5.1 解释器兼容层（已实证）

`$RANDOM` 这一块**已经解开**：把 bash 的生成器（Park-Miller + 折叠 + 去重）以 `lookupvar` hook 装进 dash，实测 **7 组种子与 bash 逐比特一致**。

- 产物：`tools/interp_compat/`（`bash_random_portable.h` + `dash-random-hook.patch` + `verify.sh`）
- 实证报告：[`INTERP_COMPAT_LAYER.md`](INTERP_COMPAT_LAYER.md)

> ⚠ **但它不是通用化的全部**：实测 patched dash 跑 V6 产物**仍然失败**，报错与原版 dash **完全相同** —— 挡在**第 2 层语法**（`declare -a` / `[[ ]]` / `<<<` / `${var//}`）。
>
> **难度排序修正**：`$RANDOM` **不是**最硬的骨头，恰恰是**最容易的一块**。真正的障碍是语法层。

### 5.2 外部方案调研（已排除歧路）

社区同类项目全量核查结果见 [`PRIOR_ART_REVIEW.md`](PRIOR_ART_REVIEW.md)。**没有一行代码可直接复用**，但排除了四条歧路，并确认了两个该补的动作。

**四条被堵死的路**（均有实测或事实支撑，不必再重复讨论）：

| 歧路 | 为什么不通 |
|---|---|
| 用 zsh `emulate bash` 拿 bash 语义 | **`emulate bash` 根本不存在**，静默退化成 `sh` 且 rc=0；且 emulate 只改 options 不改解析器；实测**完全不改变 `$RANDOM` 取值序列** |
| 给 zsh 打上游 C 补丁 | **该补丁不存在**（`Src/subst.c` 与 bash 兼容无关）；且 bash 与 zsh 是两套独立实现，无法靠补单文件获得 bash 语义 |
| 用 Zshrs 这类「多方言 drop-in」 | 宣称含 `--bash`/`--dash`，但项目 4.6 个月、110 版、代码量数字自相矛盾（190k→915k），且**明确只对 zsh 模式做差分模糊测试**，README 从未声称能跑 bash 脚本 |
| 移植 Babelfish / Reef | 两者都真实且质量不错，但目标是 **fish**，不是 POSIX sh；且面向交互场景，非无头执行 |
| 用 `libdash`（误以为的「dash 补丁」） | 它是把 dash fork 成**可链接库**，主用途是**解析**（Python/OCaml 绑定、`shell_to_json`），**不含运行时增强** —— 拿它跑产物 `declare: not found` 照样报。**名字对得上、能力对不上** |

**两个应该照搬的设计动作**：

1. **`crossrun` 式准入闸门** —— 产物发布前必须丢给 bash / dash / busybox ash 各跑一遍并比对输出。成本极低，且能立刻给出「当前产物在 dash 上具体挂在哪一行」，让 Layer 2 工作量从估计变成**可测量**。
2. **`lint` 式静态检查** —— 扫描产物、列出全部非 POSIX 构造及行号，只报告不自动修，补上 `v6_lint.py` 现在缺的这块。

**一条方法论确认**：已废弃的 `bash2zsh-complete` 失败原因是「bash 构造太多、无法穷尽支持」。映射到我们 —— **不要做通用 bash→sh 转译器，只降级我们自己产物里出现的那个有限构造集**。这正是功能剥离表的思路。

### 5.2b 靶子修正：Android 是 mksh，不是 dash（重要）

> 完整调研见 [`SHELL_TARGETS.md`](SHELL_TARGETS.md)。

**意外发现：ShellVMP 的目标平台是 Android，而 Android 的系统 shell 是 mksh，不是 dash。**

按 Android 官方 `shell_and_utilities/README.md`：**Android 4.0（ICS）起 `/system/bin/sh` 就是 mksh**（MirBSD Korn Shell），5.0 起 ash 已从树中移除。设备实测 `$KSH_VERSION` = `@(#)MIRBSD KSH R55`。

**这意味着原「档位 2：dash-only PoC」瞄错了靶子。** 而且——**mksh 的兼容性远好于 dash**：

| 构造 | bash | **mksh** | dash | zsh |
|---|---|---|---|---|
| 真数组 `a=(1 2 3)` | ✅ | ✅ | ❌ | ✅ |
| `[[ ]]` | ✅ | ✅ | ❌ | ✅ |
| `<<<` here-string | ✅ | ✅ | ❌ | ✅ |
| `${var//x/y}` | ✅ | ✅ | ❌ | ✅ |
| `${a[0]}` 下标 | ✅ | ✅ | ✅ | ✅ |
| `declare -a` | ✅ | ❌ | ❌ | ❌ |
| `for ((;;))` | ✅ | ❌ | ❌ | ❌ |
| `<(…)` 进程替换 | ✅ | ❌ | ❌ | ❌ |

**mksh 只差 4 个构造，dash 差一整片。** 实测真实产物：mksh 只报 2 类错（`declare` + `for ((`），改掉后**语法层全过**；dash 则是满屏 `Bad substitution`。

**且在 mksh 上必须改生成器而非产物**：解释器函数是产物用 `eval` 展开的，文本替换够不到（骨架里的 `declare -a`/`for ((` 能替换，`eval` 载荷里的 `<(…)` 不能）。

#### 5.2b-1 实测结果：mksh 已完成 ✅

**结论：产物在 mksh 下与 bash 输出逐字节一致**（8 轮独立生成 8/8 通过，门禁工具 `tools/sh_compat_check.sh`）。

但真正的工作量**不在上面那张表里**。语法层 4 项改完后，产物在 mksh 下**仍然静默 `exit 1`** —— 因为真正的阻塞在**第 3 层密钥链**。实测挖出**四个原清单完全没预料到的分叉源**：

| # | 构造 | bash | mksh | dash |
|---|---|---|---|---|
| 1 | `$RANDOM` | Park-Miller LCG | 另一套算法 | **没有** |
| 2 | `$-` | `hB` | `hU` | 空串 |
| 3 | **`$_`** | 上一条命令的最后一个参数 | **恒为 shell 自身路径** | 同 mksh |
| 4 | `read -a` | 按 IFS 切分字段 | **按字符码建数组** | 无 `<<<` |

**`$_` 是最隐蔽的一个**：产物用信标 `true "<随机串>"` + `rt=$_` 捕获来给每块掺入执行熵，这在 bash 下完全正确，但 mksh/dash 的 `$_` 与"上一条命令"毫无关系。修法是**不再要求 `$_` 回放任何东西**，把信标字面量内联进捕获行（`rc=$? rt="<beacon>"`）。

> **方法论教训**：`$RANDOM` 只是"看起来最像随机数"的那个坑。真正的通用化障碍是**一整套"bash 扩展语义被误当成可移植语义"的构造**。原表格只覆盖了**语法**层（能不能解析），完全没覆盖**语义**层（同一个写法解出不同的值）。**语义层比语法层危险得多**，因为它不报错。

**同时确认：zsh 不做。** zsh 是**交互 shell 不是脚本 shell** —— JetBrains 2025 显示 62% 开发者用 zsh 作交互 shell，但 CNCF 2025 显示 **94% 的 CI/CD 用 bash**，"zsh 在生产基础设施中≈0"。我们兼容的是**脚本运行环境**，zsh 在这个维度份额接近零。

> **修正后的优先级**：**mksh（P0，Android 真靶子，已完成）→ bash（已完成）→ dash（P2，成本最高）→ busybox ash（P3）→ zsh（不做）**。
>
> **止损点**（已达成）：产物在 mksh 下跑通第一个块 → **实际结果：跑通全部块，且与 bash 逐字节一致**。

### 5.3 第 2 层语法审计（r23 实测，推翻悲观估计）

> 完整审计见 [`DASH_SYNTAX_AUDIT.md`](DASH_SYNTAX_AUDIT.md)。

**原报告说第 2 层「数组下标访问遍布解释器，改动面大」—— 实测证明是错的。**

用一条 `sed`（`declare -a _X` → `_X=`）对真实产物做最小替换后：

| 构造 | 替换前 | 替换后 |
|---|---|---|
| `declare -a _Rc` | `declare: not found` | ✅ **消失** |
| `${_c[$_p]}` 下标读 | — | ✅ **dash 原生支持，零改动** |
| `${#_c[@]}` | `Bad substitution` | ✅ 消失 |

**原因**：dash 里 `${a[0]}` 就是**位置参数下标语法**（实测 `dash -c 'set -- a b c; echo ${2}'` → `b`），而我们的产物**恰好运行在这个模式上**（先 `set -- ${_Rc[@]}`，再用 `${_c[$_p]}` 访问）。

**因此数组下标全线零改动** —— 原估「要改掉所有下标访问点」**不成立**。

**但审计同时发现原报告漏掉的硬点**：产物**主解释器循环**（骨架 `1113`–`1290`）里有

| 构造 | 次数 | dash | 处置 |
|---|---|---|---|
| `<<<` here-string | **6** | ❌ 语法错 | `printf\|read`，或锁 `_pp=0` 绕过 |
| `<(…)` **进程替换** | **4** | ❌ **无原生替代** | 临时文件（**性能有损**） |
| `EPOCHREALTIME` | 2 | ❌ 空值 | `date +%s%N` |

**修正后的第 2 层 = 4 行声明 + 约 15 处构造**，其中 10 处（6 个 `<<<` + 4 个 `<(…)`）集中在主循环。`<(…)` 在 dash 里**没有原生替代**，这是真正的成本所在。

**一条可能的捷径**：产物本就有**三档 `_pp` 分派**（`builtin eval` / `source /dev/fd/9 9<<<` / `source <(…)`），**档位 0 已是纯 POSIX**。若能在 dash 下**锁死档位 0**，则 `<<<` 与 `<(…)` 全部绕过，工作量再降一个数量级。**待验证语义等价性。**

**并发不是障碍**：审计确认产物与生成器**均不使用** `coproc` / `wait` / `mkfifo` / 后台 `&`。唯一担心的因素已排除。

> **止损点（不变）**：生成一个 dash 产物，看它**能否跑通第一个块**。现在判断是**大概率能**，但需先验证「档位 0 捷径」。
>
> ⚠ **下一步优先级**：① 验证 `_pp` 档位 0 语义等价性（关键）→ ② 写跨 shell 跑通检查器 → ③ 再决定是否开工档位 2。
