# 威胁模型与能力承诺

> **这份文档是本项目最重要的部分。**
>
> 任何声称"无法破解"的脚本保护都是骗局。我们在这里**如实说明**挡得住什么、挡不住什么——因为虚假的安全承诺会让使用者做出错误的风险判断，**这比不保护更糟**。

---

## 一、攻击者模型

我们假设攻击者拥有以下能力（**按能力递增**）：

| 级别 | 能力 | 典型手段 |
|---|---|---|
| **A** | 拿到产物文件 | `cat` / `strings` / 十六进制查看 |
| **B** | 静态分析工具 | 反汇编器（IDA/Ghidra）、脚本解析、模式匹配 |
| **C** | 运行环境控制 | 调试器（gdb）、`strace`、注入（frida）、`LD_PRELOAD` |
| **D** | root 权限 | 读 `/proc/pid/mem`、`ptrace`、内核模块 |
| **E** | 无限时间 + AI 辅助 | 人工逆向 + LLM 辅助理解 |

---

## 二、防线 vs 攻击能力矩阵

| 攻击能力 | 防线 | 效果 |
|---|---|---|
| **A** 拿到文件 | V6 分块加密 | ✅ **消除**（磁盘上无明文） |
| **B** 静态分析 | V6 链式绑链 + V7-ISA 令牌化 | ✅ **大幅提高成本**（需动态执行才能解密） |
| **B** 批量扒取 | per-build 随机化 | ✅ **消除**（每次构建产物结构不同，无法写规则） |
| **C** 调试器 | V7 反调试（TracerPid）+ 调试开关剥离 | ✅ **消除**（`set -x` / `PS4` / `BASH_ENV` 全部关闭） |
| **C** 注入（frida） | V7 frida 痕迹扫描 | ⚠️ **提高成本**（能绕过，但需要定制） |
| **C** 内存 dump（非 root） | `PR_SET_DUMPABLE=0` + seccomp-BPF | ✅ **消除**（内核层拒绝） |
| **D** 内存 dump（root） | 信噪比稀释 | ⚠️ **提高成本**（能读到，但分不清真假） |
| **E** 人工逆向 | 全部手段叠加 | ⚠️ **提高成本**（目标：成本 > 脚本价值） |

> **"消除" vs "提高成本"** 是本项目最重要的区分。产品说明里必须写清哪层是哪层。

---

## 三、挡得住什么（可以承诺）

- ✅ **随手看源码** —— `cat` 产物看不到任何业务逻辑
- ✅ **静态批量扒取** —— 无法写正则/规则批量去混淆
- ✅ **明文落盘分析** —— 磁盘上不存在完整明文
- ✅ **非 root 的内存读取** —— seccomp-BPF 在内核层拒绝（**唯一确定性手段**）
- ✅ **调试追踪** —— `xtrace`/`verbose`/`BASH_ENV` 全部失效
- ✅ **篡改检测** —— Encrypt-then-MAC，改一个字节即拒绝执行
- ✅ **密钥不在文件里**（PASSKEY_MODE）—— 信息论上无法静态解密

## 四、挡不住什么（必须说清）

### 4.1 root 权限下的内存读取

**这是最根本的限制。** 解释器最终必须执行明文，而明文必然出现在内存里。

- `PROT_NONE` **拦不住** `/proc/pid/mem`（内核走 `get_user_pages`，不检查页表权限）
- 实测：8 线程高频轮询，"窗口式保护"命中率 **99.9995%**

**能做的只有**：
1. 缩短明文窗口（流式解密，即写即抹）
2. **信噪比稀释**——注入大量不可区分的冗余内容，让"识别真明文"变成算力问题

### 4.2 有足够时间的逆向

**任何混淆都是"提高成本"，不是"消除可能"。**

我们的目标不是"无法破解"，而是：

> **让逆向成本 > 你的脚本价值。**

### 4.3 运行期行为分析

即使完全无法静态解密，攻击者仍可以：
- 观察产物的**输入输出行为**，反推逻辑
- 对比多次运行的差异（差分分析）
- 在关键调用点下断点（如果绕过了反调试）

**这是"保护逻辑"和"保护行为"的区别**——我们只能保护前者。

### 4.4 一个具体的、诚实的边界说明

> 在我们的架构里，脚本最终要交给解释器 `eval`。**VMP 保护的是"壳"，`eval` 那一刻的明文没有被保护到。**
>
> 攻击者 hook `execve` 拿到内存 fd、或直接 dump 解释器内存，就能看到 `eval` 的明文。
> 这是架构决定的，**不是说 VMP 没用，而是说它保护的范围有边界**。

## 五、强度自评

```
整体强度 ≈ 最弱组件
        且所有组件共享信任根（dump 一次全暴露）
```

| 场景 | 强度评估 |
|---|---|
| 防"好奇的同事看一眼" | 🟢 极强 |
| 防"竞争对手扒取逻辑" | 🟢 强（成本远超收益） |
| 防"专业的破解团队" | 🟡 中（能拖住，但拖不住很久） |
| 防"有 root 的定向攻击" | 🔴 弱（只能稀释信噪比） |

---

## 六、设计原则（从威胁模型推导）

1. **按攻击路径分工，不按代码层次分工。** 攻击者只有四条路：静态分析 / 动态调试 / 内存 dump / 篡改机制。每个组件必须回答"我堵的是哪条"。
2. **同一条路径上套两层收益极低**，不同路径各堵一层才有意义。
3. **检测到入侵要破坏，不要报警。** 报警可绕，破坏不可绕。
4. **诚实写进产品说明。** 说不清"挡不住什么"的保护方案是不负责任的。

## 七、给使用者的建议

**如果你的脚本价值 $100**：不用本工具，或者只开 V6 默认档就行。

**如果你的脚本价值 $10,000**：全量开启 + PASSKEY_MODE + 真机构建。

**如果你的脚本价值 $1,000,000**：本工具能帮你拖住对手一段时间，但**请同时准备法律手段**——技术保护永远不是终点。

> **技术保护的目标是"提高攻击成本"，法律和商业手段才是最终保障。**
