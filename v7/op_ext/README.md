# 值算子扩展点（op_ext）

> **一句话**：这里告诉你怎么给 ShellVMP 加**自己的**值运算算子，
> 以及**为什么有些东西不该往里加**。

---

## 一、这是什么，解决什么问题

ShellVMP 的 V7-ISA 令牌化（L1-L6）解决的是**名字暴露**——命令名、关键字、
变量名、路径、字符串字面量，在产物里都是随机令牌。

但有一类逻辑它覆盖不到：**纯值运算**。

```bash
# 原脚本
sum=$(( (a + b) * 7 ))
h=$(printf '%s' "$x" | sha256sum | cut -d' ' -f1)
```

上面这两行的**表达式本身仍是明文**——算术结构、管道、命令名都在。

本扩展点把这类运算**搬到 C 层执行**：

```bash
# 编译期 v7_isa_ops.py 翻译后（产物里实际存的）
v7p_x7k2m9q1=$(v7p_9yshhevga_ v7p_3f8a1c v7p_b5e2d7 v7p_7)
v7p_h_tok=$(v7p_sha_tok v7p_x_tok)
```

```c
/* 运行期：C 层拦截 → 从 bash 变量表取值 → 算 → 写回 */
int a = v7_op_arg_long(...);   // 令牌已还原
int r = (a + b) * 7;           // ← 全程在 C 寄存器/栈上
v7_op_ret_long(out, outsz, r);
/* (a+b)*7 这段表达式文本，从未存在于产物或内存中 */
```

### 顺带的三个好处

| 收益 | 说明 |
|---|---|
| **减少语义指纹** | `sha256sum` / `cut` / `printf` 这些命令名不再出现在产物里 |
| **性能提升** | 从「fork 3 个进程 + 建管道」变成 0 个进程 |
| **收窄明文窗口** | 中间值不再以文本形式流经管道缓冲 |

## 二、五步加一个算子

```
第 1 步  在 op_example.c 里写一个 static 函数（签名照 v7_op_fn）
第 2 步  在 op_example.c 末尾的 v7_op_table[] 加一行
第 3 步  在 tools/v7_isa_ops.py 的 OP_SYMBOLS 加同名真名
第 4 步  （若另建文件）在 v7/bash_poc/build_poc.sh 的源码清单里加入
第 5 步  跑 tools/op_itest.py 回环自检
```

### 最小示例

```c
/* 第 1 步 */
static int
v7op_mod (const char *const *args, int nargs, char *out, size_t outsz)
{
    long a, b;

    if (v7_op_arg_long (args, nargs, 0, &a) != 0)
        return V7_OP_ERR_ARG;
    if (v7_op_arg_long (args, nargs, 1, &b) != 0)
        return V7_OP_ERR_ARG;
    if (b == 0)
        return V7_OP_ERR_ARG;        /* 除零：显式拒绝，不要让它崩 */

    return v7_op_ret_long (out, outsz, a % b);
}

/* 第 2 步 */
const v7_op_entry v7_op_table[] = {
    { "v7op_mod", v7op_mod, 2, 2, "取模（除零拒绝）" },
    /* ... 原有项 ... */
};
```

**就这么多。** 没有词法分析、没有语法树、没有解释器循环——
因为语法分析在**编译期**就做完了（见下节）。

---

## 三、为什么不需要写解析器

这是理解本扩展点**为什么可行**的关键。对比一下工作量：

```
「在 C 里重新实现一个 shell」
     源文本 → [词法分析] → [语法分析] → AST → [执行器] → 结果
              ↑ 巨大                     ↑ 巨大

「加一个值算子」（本扩展点）
     源文本 → [编译期翻译，已完成] → (算子id, 参数…) → [执行器] → 结果
                                                        ↑ 只写这个
```

`tools/v7_isa_ops.py` 在**编译期**已经把 `$(( (a+b)*7 ))` 变成
`v7p_x1 v7p_a v7p_b v7p_7`。运行期拿到的是**结构化的**
`(算子 id, 参数 1, 参数 2)`，**不需要再解析任何文本**。

> **类比**：写一个 Python 解释器（需要词法+语法分析，巨大）
> vs 写一个 Python 的 C 扩展模块（参数是现成的 PyObject，只写算法）。
> **你做的是后者。**

## 四、⭐ 边界声明（必读，否则会掉进工作量陷阱）

### 4.1 本扩展点只适用于纯值运算

**控制流不要做成算子。** 这不是"我们没做"，是 **bash 架构的物理下限**。

bash 的控制流分派依赖 `enum command_type`：

```c
/* bash execute_command 大致形态 */
case cm_if:    execute_if_command (cmd);    break;
case cm_for:   execute_for_command (cmd);   break;
case cm_while: execute_while_command (cmd); break;
case cm_cond:  execute_cond_command (cmd);  break;   /* [[ ]] */
```

`cm_if` 这类字段由**词法 + 语法分析阶段**填入，而该阶段
**必须面对明文 token**——不看到 `if` / `then` / `fi` 的文本，
就无法构造出 `cmd->type == cm_if`。

| 阶段 | 能否避开明文 |
|---|---|
| 词法分析（`read_token`） | ❌ 必须看文本才能识别 `if` / `then` / `fi` |
| 语法分析（`parse_command`） | ❌ 必须看明文才能建 `COMMAND` 树 |
| 展开（`expand_word`） | ❌ `$var` / `$(...)` / glob 都要看内容 |
| 执行（`execute_*`） | ✅ 只有到这里才可能控制 |

本项目现有的 L3 插桩点（`y.tab.c` 的 `CHECK_FOR_RESERVED_WORD` 宏）
正是"必须看明文"的那个位置——策略是**在看的那一刻做替换**，
而不是消除明文暴露。

### 4.2 那为什么值算子能绕开

因为值算子是**自包含**的：

```
if / for / while  → 必须由 bash 跨语句地管理状态
                    （分支栈 / 循环变量 / break-continue 目标）
                    ⇒ 搬到 C 层 = 在 C 里重建 bash 执行引擎

值运算（add/hash/substr）
                  → 输入什么输出什么，不碰 shell 状态
                  ⇒ 搬到 C 层 = 写一个纯函数
```

**把控制流虚拟化，等于重新实现整个 shell；把值运算虚拟化，等于写几个纯函数。**
这两件事的工程量差两个数量级。

### 4.3 结论

| 类别 | 能否扩展 | 建议 |
|---|---|---|
| **纯值算子**（算术 / 字符串 / 哈希 / 编码） | ✅ **可以，推荐** | 按你的脚本实际需要加 |
| **变量读写算子**（get / set） | ⚠️ 可以，但需处理 bash 变量表 API | 谨慎 |
| **单命令算子**（echo / test / printf） | ⚠️ 可参照 `v7_echo_builtin` | 谨慎 |
| **控制流算子**（if / for / while） | ❌ **不要做** | 架构下限，做了也是白做 |

## 五、攻击面契约（实现算子前必须读）

本层**不引入解析器攻击面**（没有解析器），但确实引入三类新风险。
每个算子的实现者必须自行控制：

| 风险 | 处理方式 | 范本 |
|---|---|---|
| **① 参数越界** | `substr` 的 offset/len 必须校验，禁止裸指针运算 | `op_example.c` 的 `v7op_substr` |
| **② 整数溢出** | 显式定义行为（回绕 / 饱和 / 拒绝），不能不管 | `v7op_add` 选择"拒绝" |
| **③ 缓冲长度** | 输出必须显式限长，禁止 `strcpy` 家族 | 所有算子均用 `v7_op_ret_str` |

### 为什么这几条是**真实**攻击面而不是理论问题

攻击者拿不到你的源码，但**能构造输入**。一个没做边界校验的
`substr`，在正常脚本下永远不会出问题（正常脚本不会传负 offset），
但在攻击者构造输入时会变成越界读。

**这是"源码不可读"和"输入可控"之间的落差**——源码保护得再好，
也挡不住"喂奇怪参数看行为"。

### 三条硬规则

1. **算子必须是纯函数**：给定输入，结果确定，不读写任何 bash 状态。
2. **禁止保存参数指针**：`args` 里的字符串归调用方所有，返回后即被擦除。
3. **凡是需要改变 shell 状态的，不要做成算子**——见下节。

## 六、不要把这些做成算子

| 不要做 | 原因 |
|---|---|
| `if` / `for` / `while` / `case` | 需要 bash 的分支栈、循环变量、break/continue 目标 |
| `$?` / `$_` / `PIPESTATUS` 的正确回填 | 需要与 bash 状态机同步（易错，且难以全面测试） |
| 管道 / 重定向 / 进程替换 | 需要作业控制、fd 管理 |
| `trap` / `set -e` / `shopt` | 改变解释器全局行为 |
| 任何需要 `fork` 的东西 | 性能与信号语义都会变复杂 |

> 这些不是"暂时没做"，是**架构上不该做**——它们属于 bash 执行引擎的职责，
> 搬到 C 层等于重新实现 bash 的那一部分。**收益远小于成本。**

## 七、文件清单

| 文件 | 作用 |
|---|---|
| `op_registry.h` | 接口定义（算子签名、返回码、参数访问辅助、攻击面契约） |

| 文件 | 作用 |
|---|---|
